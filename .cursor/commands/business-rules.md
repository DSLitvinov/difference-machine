# Difference Machine - Бизнес-правила и ключевая логика

> **Метаданные:** Forester хранит refs, index, manifests, reviews, locks и stash как файлы в `.DFM/` (без SQLite). См. [database.md](./database.md).

## Двухэтапный процесс коммита (Staging Area)

### Принцип работы
Forester использует двухэтапный процесс коммита, аналогичный Git:
1. **Staging** (`forester add`) — добавление файлов в индекс (staging area)
2. **Commit** (`forester commit`) — создание коммита из файлов в индексе

### Staging Area (Index)
- **Хранилище**: JSON файл `.DFM/index`
- **Формат**: `{"path/to/file": "hash", ...}`
- **Назначение**: Точный контроль над тем, какие файлы попадут в коммит

### Правила
- Коммит возможен только если индекс не пуст
- После успешного коммита индекс автоматически очищается
- Файлы с одинаковым хешем не добавляются повторно
- Игнорируемые файлы (`.dfmignore`) не попадают в индекс

### Workflow
```
1. forester add .              # Добавить файлы в staging
2. forester status             # Проверить что добавлено
3. forester commit -m "..."    # Создать коммит из staged файлов
```

## Дедупликация объектов

### Принцип
Одинаковые файлы хранятся **один раз**, независимо от того, сколько раз они были закоммичены.

### Алгоритм
1. **Вычисление хеша**: SHA256 от **несжатого** содержимого файла
2. **Проверка существования**: Если объект с таким хешем уже существует → возврат хеша
3. **Сохранение**: Если не существует → сжатие и сохранение

### Структура хранения
```
.DFM/objects/
├── blobs/sha256/ab/cdef...     # Бинарные объекты
├── trees/sha256/78/90ab...     # Деревья файлов
└── commits/sha256/cd/ef12...   # Коммиты
```

### Преимущества
- Экономия места на диске
- Быстрое сравнение файлов (по хешам)
- Гарантия целостности данных

### Пример
```
Файл model.blend появляется в 10 коммитах
→ Хранится только 1 раз
→ Все коммиты ссылаются на один хеш
```

## Хеширование

### Алгоритм
- **SHA-256** для всех объектов
- Хеш вычисляется от **несжатого** содержимого (для дедупликации)

### Типы хешей

#### Хеш файла (Blob)
```go
hash := HashFile(filePath)  // SHA256 от содержимого файла
```

#### Хеш строки
```go
hash := HashString(content)  // SHA256 от строки
```

#### Хеш коммита
```go
// Хеш вычисляется от JSON коммита БЕЗ поля hash
commitJSON := commit.ToJSON()
delete(commitJSON, "hash")
commitHash := HashString(commitJSON)
```

### Структура пути по хешу
```
Хеш: abc123def456...
Путь: ab/c123def456...
```
Первые 2 символа → директория, остальное → имя файла

## Сжатие данных

### Алгоритм
- **Zlib/Deflate** для сжатия объектов
- Сжатие применяется **только при сохранении** в хранилище
- Хеш вычисляется от **несжатого** содержимого

### Процесс сохранения Blob
```
1. Вычислить хеш от несжатого файла
2. Проверить существование (по хешу)
3. Если не существует:
   a. Сжать файл (zlib/deflate)
   b. Сохранить сжатый файл
4. Вернуть хеш
```

### Процесс чтения Blob
```
1. Прочитать сжатый файл
2. Попытаться распаковать
3. Если распаковка успешна → вернуть распакованные данные
4. Если нет → вернуть как есть (на случай старых несжатых файлов)
```

### Преимущества
- Экономия места на диске
- Быстрая передача по сети (если будет синхронизация)
- Прозрачность для пользователя

## Создание коммита

### Алгоритм

1. **Проверка индекса**
   - Индекс не должен быть пустым
   - Если пуст → ошибка: "nothing to commit"

2. **Создание дерева файлов (Tree)**
   ```
   Для каждого файла в индексе:
     - Создать TreeEntry с хешем и путем
     - Добавить в Tree
   ```

3. **Сохранение дерева**
   ```
   - Сериализовать Tree в JSON
   - Вычислить хеш дерева
   - Сохранить в .DFM/objects/trees/sha256/
   ```

4. **Создание объекта коммита**
   ```
   Commit {
     hash: (вычисляется позже)
     parent_hash: HEAD текущей ветки
     tree_hash: хеш дерева
     author: из аргументов или переменной окружения
     message: из аргументов
     timestamp: текущее время
     type: PROJECT
   }
   ```

5. **Вычисление хеша коммита**
   ```
   - Сериализовать коммит БЕЗ поля hash
   - Вычислить SHA256 от JSON
   - Установить hash в коммит
   ```

6. **Сохранение коммита**
   ```
   - Сохранить commit object в `.DFM/objects/commits/`
   ```

7. **Обновление ссылок**
   ```
   - Обновить `.DFM/refs/heads/<branch>`
   - Добавить запись в reflog
   ```

8. **Очистка индекса**
   ```
   - Очистить .DFM/index после успешного коммита
   ```

### Хуки (Hooks)
- **Pre-commit**: Выполняется перед коммитом (может отменить коммит)
- **Post-commit**: Выполняется после коммита (для уведомлений, интеграций)

## Система веток и ссылок

### Структура ссылок
```
.DFM/refs/
├── heads/          # Ветки
│   ├── main
│   └── feature-branch
├── tags/           # Теги
│   └── v1.0.0
└── HEAD            # Текущая ветка
```

### Создание ветки
```
1. Проверить существование
2. Создать файл .DFM/refs/heads/<name> с хешем коммита
```

### Переключение ветки (Checkout)
```
1. Определить тип (ветка или коммит)
2. Получить коммит и его дерево
3. Восстановить все файлы из дерева:
   - Blob → восстановить файл
4. Обновить HEAD и текущую ветку
5. Выполнить post-checkout hook
```

### Правила
- Ветка может быть пустой (orphan branch) — без коммитов
- HEAD ветки хранится в `.DFM/refs/heads/<branch>`
- Удаление ветки не удаляет коммиты

## Reflog и безопасное удаление коммитов

### Принцип
Коммиты **не удаляются сразу**, а помечаются для удаления через reflog.

### Процесс удаления коммита

1. **Проверки перед удалением**
   ```
   - Не является HEAD активной ветки
   - Не имеет дочерних коммитов
   - Не ссылается тегами
   ```

2. **Помечание для удаления**
   ```
   - Добавить запись в reflog с operation="delete"
   - Коммит скрывается из истории
   - Но остается в object store
   ```

3. **Восстановление**
   ```
   - Удалить запись "delete" из reflog
   - Коммит снова появляется в истории
   ```

### Garbage Collection

**Условия удаления коммита:**
1. Помечен для удаления в reflog
2. Истек срок хранения reflog (по умолчанию 90 дней)
3. Нет активных ссылок (ветки, теги)
4. Нет дочерних коммитов

**Процесс GC:**
```
1. Получить все записи reflog с operation="delete"
2. Найти записи с истекшим сроком
3. Проверить отсутствие ссылок
4. Физически удалить коммит (ForceDeleteCommit)
5. Очистить истекшие записи reflog
```

### Преимущества
- Безопасность: можно восстановить "удаленные" коммиты
- Гибкость: срок хранения настраивается
- Надежность: коммиты не теряются случайно

## Stash (Временное сохранение)

### Назначение
Сохранение незакоммиченных изменений без создания коммита.

### Процесс сохранения

1. **Создание дерева из текущего состояния**
   ```
   - Просканировать рабочую директорию
   - Игнорировать .DFM и файлы из .dfmignore
   - Для каждого файла:
     * Вычислить хеш
     * Сохранить blob
     * Добавить в дерево
   ```

2. **Сохранение дерева**
   ```
   - Сохранить tree в хранилище
   - Получить tree_hash
   ```

3. **Создание stash записи**
   ```
   Stash {
     hash: HashString(stashJSON)
     message: сообщение пользователя
     tree_hash: хеш дерева
     created_at: текущее время
   }
   ```

4. **Сохранение**
   ```
   - Записать JSON в `.DFM/stash/`
   ```

### Применение Stash

**Apply** (применить без удаления):
```
1. Получить stash по хешу
2. Получить дерево из tree_hash
3. Восстановить все файлы из дерева
4. Stash остается в списке
```

**Pop** (применить и удалить):
```
1. Выполнить Apply
2. Удалить stash-файл из `.DFM/stash/`
```

### Правила
- Stash не сохраняет состояние Blender (только файлы)
- Можно применять многократно (Apply)
- Stash хранится до явного удаления

## Блокировка файлов

### Назначение
Предотвращение конфликтов при совместной работе над файлами.

### Типы блокировок

**Exclusive (исключительная)**
- Только один пользователь может заблокировать файл
- Другие пользователи не могут заблокировать

**Shared (разделяемая)**
- Несколько пользователей могут заблокировать файл
- Полезно для чтения

### Процесс блокировки

1. **Проверка существующей блокировки**
   ```
   - Проверить `.DFM/locks/` (JSON)
   - Учесть истекшие блокировки (expires_at)
   ```

2. **Создание блокировки**
   ```
   Lock {
     file_path: путь к файлу
     user: имя пользователя
     branch: текущая ветка
     lock_type: EXCLUSIVE или SHARED
     created_at: текущее время
     expires_at: время истечения (0 = никогда)
   }
   ```

3. **Сохранение**
   ```
   - Записать JSON в `.DFM/locks/`
   ```

### Правила
- Блокировка привязана к ветке
- Истекшие блокировки игнорируются автоматически
- Только владелец блокировки может её снять

## Сравнение версий (Diff)

### Типы сравнения

**HEAD vs Working Directory**
```
forester diff
- Сравнить дерево HEAD с текущими файлами
```

**Два коммита**
```
forester diff <commit1> <commit2>
- Сравнить деревья двух коммитов
```

**Коммит vs HEAD**
```
forester diff <commit>
- Сравнить коммит с HEAD текущей ветки
```

### Алгоритм сравнения

1. **Получение деревьев**
   ```
   - Получить tree_hash из коммитов
   - Загрузить деревья из хранилища
   ```

2. **Построение карт**
   ```
   tree1Map: path → TreeEntry
   tree2Map: path → TreeEntry
   ```

3. **Определение изменений**
   ```
   Added: файлы в tree2, но не в tree1
   Modified: файлы с разными хешами
   Deleted: файлы в tree1, но не в tree2
   ```

4. **Unified Diff (опционально)**
   ```
   - Только для текстовых файлов
   - Показывает изменения построчно
   - Цветовая подсветка
   ```

### Правила
- Бинарные файлы показывают только изменение хеша
- Текстовые файлы показывают построчные изменения
- Цвета можно отключить (`--no-color`)

## Checkout (Переключение версий)

### Процесс

1. **Определение цели**
   ```
   - Проверить, является ли это веткой
   - Если нет → попытаться найти коммит по хешу
   ```

2. **Получение коммита и дерева**
   ```
   - Загрузить commit object из `.DFM/objects/commits/`
   - Получить tree_hash
   - Загрузить дерево из хранилища
   ```

3. **Восстановление файлов**
   ```
   Для каждого entry в дереве:
     - Если blob:
       * Получить содержимое blob
       * Записать в файл
   ```

4. **Обновление ссылок**
   ```
   - Обновить HEAD ветки
   - Обновить текущую ветку
   - Выполнить post-checkout hook
   ```

### Правила
- Рабочая директория перезаписывается
- Незакоммиченные изменения могут быть потеряны (нужен stash)
- Пустые ветки (orphan) можно переключить

## Система Review

### Комментарии

**Создание комментария**
```
Comment {
  asset_type: "mesh" | "blob" | "commit"
  asset_id: хеш или ID ресурса
  author: автор комментария
  content: текст комментария
  x, y: координаты для 3D контента
  resolved: флаг разрешения
}
```

**Правила**
- Комментарии привязаны к ресурсу (asset_type + asset_id)
- Можно разрешить комментарий (resolved = true)
- Координаты для привязки к 3D объектам

### Одобрения

**Создание одобрения**
```
Approval {
  asset_type: тип ресурса
  asset_id: ID ресурса
  author: автор одобрения
  status: "pending" | "approved" | "rejected"
  comment: комментарий к одобрению
}
```

**Правила**
- Один автор может иметь только одно одобрение на ресурс (UNIQUE)
- Статус можно изменить (INSERT OR REPLACE)
- Используется для workflow одобрения изменений

## Игнорирование файлов (.dfmignore)

### Формат
Аналогичен `.gitignore`:
```
# Комментарий
*.tmp
.DFM/
build/
*.blend1  # Backup файлы Blender
```

### Применение
- При добавлении файлов в индекс (`forester add`)
- При создании stash
- При сканировании рабочей директории

### Правила
- Файлы в `.dfmignore` не отслеживаются
- Паттерны поддерживают wildcards (`*`, `?`)
- Можно игнорировать директории

## Хуки (Hooks)

### Типы хуков

**Pre-commit**
- Выполняется перед созданием коммита
- Может отменить коммит (вернуть ошибку)
- Переменные окружения: `FORESTER_REPO_PATH`, `FORESTER_BRANCH`

**Post-commit**
- Выполняется после успешного коммита
- Не может отменить коммит
- Переменные: `FORESTER_REPO_PATH`, `FORESTER_BRANCH`, `FORESTER_COMMIT_HASH`

**Pre-checkout**
- Выполняется перед checkout
- Может отменить переключение
- Переменные: `FORESTER_REPO_PATH`, `FORESTER_COMMIT_HASH`

**Post-checkout**
- Выполняется после checkout
- Не может отменить переключение

### Правила
- Хуки — это исполняемые скрипты
- Exit code 0 = успех, не 0 = ошибка
- Pre-хуки могут отменить операцию
- Post-хуки выполняются асинхронно (не блокируют)

## Работа с 3D-моделями

### Хранение .blend файлов
3D-модели (Blender файлы) хранятся как обычные blob объекты в `.DFM/objects/blobs/sha256/`.

### Правила
- .blend файлы коммитятся как обычные файлы через `forester add`
- Дедупликация работает на уровне файла (по хешу содержимого)
- Файлы сохраняются в assets директории проекта и коммитятся как blob'ы

## Обработка ошибок

### Принципы
- Критические записи метаданных — атомарная запись файлов (`WriteFileAtomic`)
- Проверка существования перед операциями
- Информативные сообщения об ошибках

### Типичные ошибки
- "not a Forester repository" — не найден `.DFM`
- "nothing to commit" — пустой индекс
- "commit not found" — коммит не существует
- "cannot delete commit" — коммит защищен (HEAD, children, tags)

## Производительность

### Оптимизации
- **Дедупликация** — одинаковые файлы хранятся один раз
- **Сжатие** — экономия места на диске
- **Кэширование путей** — в аддоне Blender

### Ограничения
- Большие файлы могут медленно хешироваться
- GC может быть медленным на больших репозиториях

## Безопасность данных

### Целостность
- Хеши SHA256 гарантируют целостность объектов
- Атомарная запись файлов метаданных

### Восстановление
- Reflog позволяет восстановить удаленные коммиты
- Диагностика object store (`forester rebuild`)
- Резервное копирование — копирование всей `.DFM/`

## Специальные случаи

### Orphan Branch (пустая ветка)
- Ветка без коммитов (commit_hash = NULL)
- Можно создать и переключиться на неё
- Первый коммит создаст HEAD

### Удаление единственного коммита
- Если коммит единственный в ветке → ветка становится orphan
- Коммит помечается для удаления
- Ветка остается, но без HEAD

### Короткие хеши
- Можно использовать первые 8 символов хеша
- Система найдет полный хеш по префиксу
- Работает для коммитов, stash, тегов
